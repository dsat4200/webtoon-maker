# Mesh handle and smoothness interaction — 2026-09-26

The final implementation renders bounded previews during mesh-handle and
smoothness-slider gestures, requests an exact redraw on release, and reduces
triangle-rejection overhead without changing exact sampling. The saved
`slam.png` 6×4 handle now renders movement previews in about 108 ms, compared
with roughly 1941 ms for the earlier exact paints. Smoothness previews take
106 ms. **Release still pauses for about 1.4 seconds to finish the exact image.**
This improves live editing substantially but does not reach 60 Hz interaction.

## Release-only check and cost profile

A separate handle-only replay exposed a missing repaint request on release:
the preview remained visible indefinitely until another UI event triggered a
paint. The combined replay masked this scheduling bug. That intermediate
`profile-release-6x4` run failed its 60-second readiness deadline; its finished
image differed from the exact oracle and is not accepted output. Root fixed
the handle release to request a repaint explicitly.

`profile-fixed-release-6x4` then completed independently with zero oracle
differences. Before the final kernel change, `_triangle_map` accounted for
1.673 of 2.327 profiled release seconds (102 calls), and .116 of .182 profiled
preview seconds. These diagnostic timings identified repeated triangle scans;
they are separate from final unprofiled timing. Earlier `current-6x4` and both
profile runs remain preserved as intermediate evidence.

## Reproducer and baseline

`tests/benchmark_mesh_interaction.py` uses a hidden native OpenGL Canvas with
the real saved 1280×1789 image and mesh modifier. It calls the actual modifier
handle begin/move/finish methods, and drives the actual smoothness slider's
pressed/valueChanged/released signals. A separate producer posts fixed-deadline
events; there is no per-move repaint or wait for rendering. Each gesture receives
60 moves in one second, plus press/release: 124 events total.

The original saved grid is 4×4. The observed live UI has 6 rows and 4 columns.
The primary comparison changes rows through `DistortControls.set_value`, which
resets the grid exactly as the UI does. It therefore matches mesh complexity,
but does not reconstruct unsaved live handle positions. Only the selected slam
object is soloed. Camera center is (540, 19800), scale .45, rotation 0°, at
1000×850 logical pixels. This isolates modifier behavior and excludes MainWindow
ancillary refresh; it is not a full recording replay or physical input latency.

An earlier supplementary 4×4 run (`baseline`) similarly queued input by up to
1703 ms, but its paint hook was installed after Qt virtual dispatch binding and
recorded no paint durations. The 6×4 run corrects that instrumentation; do not
use the supplementary run for paint-count comparisons.

## Safety and fidelity

The pre-fix snapshot contains 125 verified byte-identical Python source files in
`baseline-source`. Each run records its complete Python source hashes and the
consumed copied chapter/image hashes before and after. All edits remain in
memory; no original or copied project is saved. No MainWindow, broker, Blender
controller or Blender connection is instantiated. Settings are redirected to
the run artifact directory, and the native widget cannot show or activate.

The existing native framebuffer is saved after all input and jobs finish.
Projection, effect outputs, captured sources and prepared Distort caches are
then cleared, asynchronous projection and viewport culling disabled, and a
synchronous exact render supplies a strict finished-pixel oracle. Input queue
delay, paint duration and heartbeat gaps are separate measurements. A transient
preview is counted explicitly and is never accepted as finished output.
